# ADR-0008: Streaming upload and multipart ownership

## Status

`accepted`

## Background

Buffered `HttpBody` is intentionally bounded to request-sized values that a
caller can hold in memory. It cannot safely represent a 1 GiB file or a
multipart form containing large files. WinHTTP provides `WinHttpWriteData` for
incremental request bodies, but the request must declare a stable total length
or explicitly use the WinHTTP ignored-total-length mode. Uploads also have a
different failure invariant from downloads: the local source must never be
modified, while a remote server may have received a prefix before a timeout or
cancellation is observed.

## Decision

- Add `HttpClient.UploadFile` and `HttpClient.UploadMultipart` as additive
  synchronous APIs. They require the configured transport to implement
  `IHttpUploadTransport`; the default COM transport rejects the capability
  before opening network or file handles. The native transport is the Phase 7
  implementation.
- Uploads use `POST` and always calculate a deterministic total content length
  before `WinHttpSendRequest`. The native call sends no optional body and then
  writes at most 64 KiB per `WinHttpWriteData` call. If the total exceeds the
  signed VBA `Long` range, an explicit decimal `Content-Length` header is sent
  and `WINHTTP_IGNORE_REQUEST_TOTAL_LENGTH` is passed. Transfer-Encoding
  chunked is not exposed as a caller option in Phase 7.
- `HttpUploadResult` returns response status, reason, headers, negotiated
  protocol, request bytes written, request content length, elapsed time, and
  `AuthenticationChallenged` for status 401 or 407. HTTP status failures are
  returned normally and can be raised with `RaiseForStatus`.
- `IHttpProgressSink` is reused. It receives an initial zero-byte callback and
  callbacks after each bounded native write. `TotalBytes` is the known request
  content length. Cancellation and total-deadline checks occur before opening
  the request, before each file read/write, and after each write. A blocking
  native write remains bounded by the request send timeout.
- `UploadFile` reads an existing source file through a bounded reader. The
  source path is normalized and opened read-only; the source is never replaced,
  truncated, or deleted. If its size changes during the call, the operation
  fails rather than silently publishing a mismatched content length.
- `HttpMultipartForm` owns ordered field and file parts. Field text is UTF-8
  encoded in bounded chunks. File bytes are read in bounded chunks. Part
  headers and the final boundary are emitted incrementally; the complete
  multipart payload is never materialized as one `String` or `Byte()`.
- A multipart boundary is generated by the library and may be overridden for
  deterministic tests. Names, filenames, content types, and boundaries reject
  CR, LF, quotes, and other header-injection characters. File parts use an
  explicit or derived basename and default to `application/octet-stream`.
- No retry or replay is performed after a 401/407 authentication challenge,
  cancellation, timeout, write failure, or partial remote upload. The source
  remains available for a caller-controlled new attempt; a future auth
  provider/retry ADR may define a replayable source contract.
- Native request, connection, session, reader, and writer references are
  closed on both success and failure. Cleanup errors never replace the
  original upload error.

## Consequences

- A 1 GiB upload has bounded VBA working memory and a predictable
  `Content-Length`, at the cost of reading the source twice for multipart size
  calculation only when the caller changes a source during execution.
- Fixed-length uploads interoperate with servers that reject chunked request
  bodies and make server-side hash verification deterministic. Callers cannot
  opt into an unknown-length body in Phase 7.
- Cancellation is cooperative and cannot undo bytes already accepted by a
  remote server. The local source and native handles remain safe to reuse.
- Multipart field values remain caller-owned VBA strings, but the encoder does
  not create a second payload-sized representation. Large file parts are never
  loaded into a `Byte()` or `String`.
- Authentication challenge handling is deliberately conservative. A 401/407
  result is observable without risking an automatic replay of credentials or a
  non-idempotent body.
