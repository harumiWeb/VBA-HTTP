# Release artifact checksum contract

Release publication produces three related files beside the requested workbook
output:

- `VBA-HTTP.xlsm`, the filtered workbook produced by `xlflow build`;
- `VBA-HTTP.xlsm.build.json`, the xlflow build manifest; and
- `VBA-HTTP.xlsm.checksum.json`, a deterministic SHA-256 sidecar covering the
  first two files.

The sidecar is generated by `tools/Write-ReleaseChecksums.ps1` only after
`xlflow build` reports a successful VBE compile, save, close, and atomic
publication. `tools/Verify-ReleaseChecksums.ps1` is the authoritative validator
used by `tools/Validate-ReleaseArtifact.ps1` before component inspection or
consumer smoke execution.

## Sidecar schema

The sidecar is UTF-8 JSON without a BOM and ends with one platform newline. It
contains no timestamps, host paths, or other run-specific values, so unchanged
artifact and manifest bytes produce byte-identical sidecars.

```json
{"schema_version":1,"algorithm":"SHA-256","artifact":"VBA-HTTP.xlsm","artifact_sha256":"<64 lowercase hex characters>","manifest":"VBA-HTTP.xlsm.build.json","manifest_sha256":"<64 lowercase hex characters>"}
```

`artifact` and `manifest` are file names, not arbitrary paths. The validator
requires both names to match the files next to the supplied artifact and then
recomputes both hashes from disk. A missing, malformed, stale, or tampered
sidecar fails closed before release smoke can run.

## Publication and failure behavior

The writer computes both hashes before it writes anything. It writes the JSON
to a unique temporary file in the artifact directory, then atomically replaces
an existing sidecar with `System.IO.File.Replace` (or moves the file into place
when no sidecar exists). A failed write leaves the prior sidecar untouched; a
stale sidecar cannot pass validation because the artifact or manifest hash no
longer matches.

`xlflow build` remains responsible for atomically publishing the workbook and
its build manifest. The checksum sidecar is evidence for that already-published
pair, not a replacement for xlflow's VBE compile or publication result. Release
tasks therefore run in this order:

1. validate the dry-run component plan;
2. run `xlflow build` to the separate release output;
3. generate the checksum sidecar; and
4. validate the manifest, component set, sidecar, and external consumer smoke.

The tracked development workbook is never used as the checksum output and is
never overwritten by this process. Generated release files remain ignored by
Git; a release evidence bundle must preserve the workbook, build manifest, and
checksum sidecar together.

## Verification

- `task test:release-checksum` exercises deterministic regeneration, artifact
  tamper detection, missing-input failure, and preservation of the previous
  sidecar after a failed generation attempt.
- `task release:build` generates the sidecar and `task release:smoke` verifies
  it before opening the release workbook.
- The release gate records the sidecar with the build manifest and artifact so
  a consumer can independently recompute SHA-256 without running Excel.
